# ADR-0018: Idempotency-Key บังคับตอนบันทึกรายการซื้อขาย

- **สถานะ:** Accepted
- **วันที่:** 2026-11-04
- **เกี่ยวข้อง:** [phase 1 spec](../superpowers/specs/2026-10-05-phase-1-design.md) หัวข้อ 7 และ 9, [แผน milestone 7](../superpowers/plans/2026-11-02-milestone-7-transactions.md), [ADR-0003](0003-decimal-and-event-replay.md), [ADR-0009](0009-concurrency-row-lock-and-optimistic-locking.md)

## บริบท
การบันทึกรายการซื้อขายเป็นการสร้างข้อมูลที่ client ลองซ้ำได้ (timeout, ผู้ใช้กดซ้ำ, proxy ส่งซ้ำ) ถ้าไม่มีการป้องกัน การลองซ้ำที่ฝั่งเซิร์ฟเวอร์สำเร็จแล้วแต่ client ไม่ได้รับคำตอบจะบันทึกรายการซ้ำ ทำให้จำนวนหุ้นและต้นทุนผิดโดยผู้ใช้ไม่รู้ รายการซื้อขายสองรายการที่เหมือนกันทุกฟิลด์เป็นเรื่องที่เกิดขึ้นจริงได้ จึงตัดรายการซ้ำตามเนื้อหาไม่ได้

## ทางเลือกที่พิจารณา
1. ไม่ป้องกัน แล้วให้ผู้ใช้ลบรายการซ้ำเอง
2. ตัดรายการที่เนื้อหาเหมือนกันในช่วงเวลาสั้นๆ: ผิดเมื่อผู้ใช้ตั้งใจซื้อซ้ำ
3. ให้ client สร้าง id ของรายการแล้วใช้ `PUT`: เปลี่ยนรูปแบบ API และต้องกัน id ชนข้ามผู้ใช้
4. Header `Idempotency-Key` ที่ client สร้าง เก็บผลของคำขอแรกไว้และคืนซ้ำ

## การตัดสินใจ
เลือกข้อ 4 และบังคับส่ง (ไม่ส่ง → 400)
- key ยาว 1–128 ตัว ASCII ที่พิมพ์ได้ ผูกกับ (ผู้ใช้, พอร์ต, operation `transactions.create`) เป็น primary key ของ `idempotency_keys`
- เก็บ SHA-256 ของคำขอที่ canonical แล้ว (`request_hash`) และ representation ของรายการที่ตอบกลับ (jsonb ไม่เกิน 16 KiB, ไม่เก็บ cookie/header)
- key เดิม + คำขอเดิม → คืน `201` กับ body เดิมทุกไบต์ โดยไม่สร้างรายการ ไม่เพิ่ม version และไม่เขียน audit success ซ้ำ; key เดิม + คำขอต่าง → `409 idempotency_conflict`
- อ่าน key, ตรวจยอด, เขียนรายการ, เขียน idempotency record และ audit อยู่ใน DB transaction เดียวใต้ row lock ของพอร์ต จึงไม่มีสองคำขอที่ใช้ key เดียวกันสำเร็จทั้งคู่ (primary key เป็นแนวป้องกันสุดท้าย)
- record หมดอายุใน 24 ชั่วโมง; key ที่หมดอายุถูกลบแล้วใช้ซ้ำได้; การลบพอร์ตที่ว่างลบ record ของพอร์ตนั้นใน transaction เดียวกัน; `cmd/maintenance` ลบที่หมดอายุแล้ว (ADR-0021)

## ผลที่ตามมา
- การลองซ้ำปลอดภัย และ client ที่ลองใหม่ได้ผลลัพธ์เดิม แม้ไม่ทราบว่าครั้งแรกสำเร็จหรือไม่
- ทุก client ต้องสร้าง key (UUID ก็พอ) และเก็บไว้ตลอดการลองใหม่; การลองซ้ำหลัง 24 ชั่วโมงถือเป็นคำขอใหม่
- การแก้และลบรายการไม่ใช้ key เพราะซ้ำแล้วปลอดภัยอยู่แล้วด้วย `If-Match` (ADR-0009)
- ตารางเก็บ result เพิ่มขนาด DB ราว 1 KiB ต่อรายการ ภายใน 24 ชั่วโมง
